# ip_cheker_2 — карта файлов и запуск

Бот проверяет доступность IPv4 и целых `/24`, ведёт историю, личный список мониторинга
и раз в час сообщает **в нужную тему супергруппы только об изменениях** статуса.

Стек: Python 3.11, aiogram 3.31.0. Данные — SQLite (`data/bot.db`), один файл.
ICMP — локальный `ping` через subprocess, **напрямую**; `PROXY_URL` относится только к связи бота с Telegram.

## Запуск

```bash
python -m venv venv
venv\Scripts\activate          # Windows;  Linux/macOS: source venv/bin/activate
pip install -r requirements.txt
copy .env.example .env         # Linux/macOS: cp
# заполнить .env: TOKEN, ADMIN_ID, ALERT_CHAT_ID
python main.py
```

`.env`:

| Ключ | Смысл |
|---|---|
| `TOKEN` | токен бота |
| `ADMIN_ID` | твой Telegram id; `0` = админка выключена |
| `ALERT_CHAT_ID` | id супергруппы для алертов (бот должен быть участником); `0` = не слать |
| `ALERT_THREAD_ID` | id темы (topic) внутри супергруппы; `0` = слать без темы (General) |
| `PROXY_URL` | `socks5://user:pass@host:port` — только для Telegram, на ping не влияет |
| `DATA_DIR` | папка данных, по умолчанию `data` |
| `PING_LIMIT` | стартовый лимит одновременных пингов (потом меняется в админке) |
| `CHECK_INTERVAL` | период мониторинга в секундах (3600) |
| `MAX_WATCH` | сколько IP можно держать в мониторинге одному пользователю |
| `SCAN_MAX_IPS` | сколько адресов проверяется за один скан (1024 = четыре /24) |
| `PROXY_PORT` | порт SOCKS5 в команде для участника (1080) |
| `PROXY_CHECK_INTERVAL` | как часто проверять прокси и переключаться (60 c) |
| `PROXY_WAIT_HOURS` | сколько ждём запуска прокси участника (24 ч) |
| `PROXY_MAX_PER_USER` | сколько прокси может зарегистрировать один участник (3) |

Нужен системный `ping`: Windows — есть из коробки; Debian/Ubuntu — `apt install iputils-ping`.

## Где лежат данные и почему они не теряются

Всё в **одном файле SQLite**: `data/bot.db` (`DATA_DIR` задаёт папку).

| Таблица | Что хранит |
|---|---|
| `users` | кто писал боту (регистрация через middleware) |
| `history` | сканы, последние 50 на пользователя |
| `tracked` | личный мониторинг: IP + последний статус |
| `settings` | то, что админ меняет на ходу (лимит пингов, активный прокси) |
| `proxies` | прокси участников: доступы, статус, время последней проверки |

Рядом лежат только `results/result_<uid>.txt` (отчёты по /24) и `logs/bot.log`.

Почему не теряется:

- `PRAGMA journal_mode=WAL` + `PRAGMA synchronous=FULL` — транзакция попадает на диск до подтверждения.
  Проверено: процесс убит через `os._exit(9)` (аналог `kill -9`) — в новом процессе все данные на месте.
- В Docker файл лежит в **именованном томе** `bot_data:/app/data`. Том переживает
  `docker compose down`, `up`, пересборку образа и обновление кода.
  Данные удалит только `docker compose down -v` (или ручное удаление тома).
- Старые JSON из предыдущей версии переносятся в БД автоматически при первом старте
  (`users.json` → таблица `users` и т.д.), файлы переименовываются в `*.json.migrated`.

Бэкап и просмотр:

```bash
# из контейнера
docker compose exec bot python -c "import sqlite3; c=sqlite3.connect('/app/data/bot.db'); c.execute('VACUUM INTO \'/app/data/backup.db\')"
docker compose cp bot:/app/data/backup.db ./backup.db

# обычный bind-mount: просто скопировать файл
cp data/bot.db backup-$(date +%F).db
```

## Сеть прокси участников (/get_proxy)

Идея: участники поднимают у себя SOCKS5, бот умеет через них работать и следит за ними.

0. **Пароль — только в личке.** В группе `/get_proxy` (и кнопка «Получить команду») отвечает
   без секретов и даёт кнопку-ссылку `t.me/<bot>?start=get_proxy`. По ссылке в личном чате
   бот сразу выдаёт команду и спрашивает IP. Так пароль не остаётся в истории группы.
1. Участник пишет **`/get_proxy`** в личке → бот выдаёт готовую команду с **сгенерированными** логином и паролем:
   ```
   docker run -d --name socks5 --restart always -p 1080:1080 \
     -e PROXY_USER=u1a2b3c -e PROXY_PASSWORD=<24 hex> serjs/go-socks5-proxy
   ```
   и просит IP сервера в явном формате: `162.35.229.164` или `162.35.229.164:1080`
   (можно и сразу `/get_proxy 1.2.3.4`). При неверном формате бот объясняет ошибку
   и **ждёт повторного ввода** — заново `/get_proxy` не нужен; выход — `/cancel`.
2. Бот ставит заявку в статус **waiting** и каждые `PROXY_CHECK_INTERVAL` секунд проверяет
   **весь путь**: SOCKS5 → авторизация → TLS до `api.telegram.org`. Открытый порт сам по себе не считается.
3. Как только прокси ответил — в чат уведомлений (та же тема, что и алерты) приходит
   «✅ @участник, прокси запущен и работает».
4. Если прокси упал — бот **тэгает владельца** в той же теме и подсказывает `docker logs socks5`.
   Восстановился — сообщает об этом. Не поднялся за `PROXY_WAIT_HOURS` — заявка снимается.
5. **Авто-переключение**: если текущий путь до Telegram мёртв, бот берёт первый живой прокси
   участника и меняет сессию на ходу (`Bot.session`), запоминая выбор в БД.
   Когда основной прокси из `.env` оживает — возвращается на него.
6. `/proxies` — свой список (админ видит все) с кнопками удаления; админу доступна кнопка
   «🔌 Подключить» для ручного переключения на конкретный прокси.

Что учтено по безопасности и надёжности:

- Пароль **никогда** не показывается в списках и логах: `socks5://user:***@host:port`.
- Удалить прокси может только владелец или админ, подключать вручную — только админ.
- Не больше `PROXY_MAX_PER_USER` заявок на человека.
- Трафик до Telegram идёт по TLS внутри SOCKS5, поэтому прокси видит только адрес
  `api.telegram.org`, но **не токен и не содержимое**. Всё же злой прокси может рвать связь —
  бот это заметит и переключится.
- Мёртвый прокси **на старте** больше не убивает бота: `preflight` пробует прокси участников,
  а `run_polling` перезапускает polling с восстановлением связи вместо падения контейнера.

## Почему бот мог не запускаться с прокси

Реальный случай из этого проекта:

```
PROXY_URL="socks5://admin:пароль@162.35.229.164:1080"
```

Сам прокси был **исправен** (проверено: TCP открыт, SOCKS5-туннель до Telegram проходит).
Ломали **кавычки**: через `env_file`/окружение значение может доехать вместе с ними, и тогда
`aiohttp-socks` падает с `ValueError: Invalid scheme component:` ещё до первого запроса.

Теперь `config.unquote()` снимает обрамляющие кавычки и пробелы у **любого** значения из
окружения и `.env`, поэтому такой `.env` работает. Плюс диагностика различает причины:
неверный токен → «проверь TOKEN», мёртвый прокси → подсказка про `host.docker.internal`.

## Запуск в Docker

```bash
cp .env.example .env      # заполнить TOKEN, ADMIN_ID, ALERT_CHAT_ID, ALERT_THREAD_ID, PROXY_URL
docker compose up -d --build
docker compose logs -f bot
```

Проверить окружение внутри контейнера (главная команда при проблемах):

```bash
docker compose exec bot python -m utils.selfcheck
```

Она печатает два verdict'а и конкретные подсказки:

```
[ping] OK: ICMP работает (ping 127.0.0.1 прошёл)
[telegram] OK: Telegram доступен: @your_bot (прокси: socks5://host.docker.internal:1080)
```

Что уже учтено в `Dockerfile` / `docker-compose.yml`:

| Решение | Зачем |
|---|---|
| `iputils-ping` в образе | без него ICMP невозможен; Debian ставит `/usr/bin/ping` с capability `cap_net_raw=ep` |
| `USER appuser` (uid 1000) | бот не root; ping при этом работает (capability или sysctl) |
| `sysctls: net.ipv4.ping_group_range: "0 2147483647"` | запасной путь ICMP: непривилегированные ICMP-сокеты, работает даже с `no-new-privileges` |
| `extra_hosts: host.docker.internal:host-gateway` | прокси на хосте доступен по имени и на Linux тоже |
| `init: true` | PID 1 жнёт зомби от `ping` и передаёт SIGTERM (aiogram завершает polling штатно) |
| том `bot_data:/app/data` | `bot.db`, результаты и логи переживают пересборку; владелец — appuser, `chown` не нужен |
| `env_file: .env` | секреты передаются переменными окружения и **не попадают в образ** |
| `DATA_DIR=/app/data`, `ENV_FILE=/app/data/.env` | все изменяемые файлы внутри тома |
| `TZ` + `tzdata` | время в истории и логах; по умолчанию UTC, поставь `TZ=Europe/Moscow` |
| `HEALTHCHECK` на ping | «здоров» = контейнер реально может пинговать |
| выборочный `COPY` + `.dockerignore` | в образе нет тестов, `.env`, `data/`, `venv/` |

Хочешь видеть `bot.db` прямо в папке проекта — замени именованный том на bind-mount:

```bash
mkdir -p data && sudo chown 1000:1000 data     # контейнер работает под uid 1000
# в docker-compose.yml: закомментируй bot_data:/app/data, раскомментируй ./data:/app/data
```

Обновление после правки кода: `docker compose up -d --build`. Логи: `docker compose logs -f bot`.

### Прокси в Docker: что реально ломается

Проверено на коде aiogram 3.31 + aiohttp-socks 0.12, а не «по памяти»:

1. **`127.0.0.1` в `PROXY_URL` — это сам контейнер, а не хост.** Самая частая причина «бот не стартует в Docker».
   Лечится: `socks5://host.docker.internal:1080` (compose уже пробрасывает host-gateway),
   либо IP хоста в docker-сети, либо имя сервиса прокси в той же сети, либо `network_mode: host`.
2. **Прокси должен слушать не только loopback.** Если он забинден на `127.0.0.1` хоста, из контейнера
   будет `ProxyConnectionError: Couldn't connect to proxy`. Пусть слушает `0.0.0.0` (или адрес моста)
   и пускает подсеть контейнеров (обычно `172.16.0.0/12`). Иначе — `network_mode: host` на Linux.
3. **Схема только `socks5://` (или `http://`).** aiogram сам ставит коннектору `rdns=True`,
   то есть DNS резолвит прокси — отдельный «socks5h» не нужен. Более того,
   **`socks5h://` не поддерживается** aiohttp-socks и уронит бота на старте (`Invalid scheme component`).
4. **`HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` не работают.** aiogram создаёт `ClientSession`
   без `trust_env`, поэтому переменные окружения игнорируются. Действует только `PROXY_URL`
   из `.env` или `proxy`, заданный в админ-панели (применяется после перезапуска).
5. **DNS контейнера не обязан резолвить `api.telegram.org`** при SOCKS-прокси (резолвит прокси),
   но имя самого прокси лучше писать IP-адресом.
6. **Ping через прокси не ходит вообще.** Прокси влияет только на связь с Telegram;
   доступность сканируемых адресов зависит от сети контейнера, а не от прокси.

| Симптом в логах | Причина | Что делать |
|---|---|---|
| `ProxyConnectionError ... 127.0.0.1:1080` | прокси указан как localhost | `host.docker.internal` / IP хоста / `network_mode: host` |
| `Couldn't connect to proxy` на верном адресе | прокси слушает только loopback или режет подсеть docker | забиндить `0.0.0.0`, разрешить `172.16.0.0/12` |
| `Invalid scheme component: socks5h` | неподдерживаемая схема | заменить на `socks5://` |
| `TelegramUnauthorizedError` | неверный/отозванный токен | проверить `TOKEN`; прокси ни при чём |
| `Temporary failure in name resolution` | DNS контейнера, прокси не задан | задать прокси или починить DNS в docker |
| все IP «недоступны», `ping: socket: Operation not permitted` | ICMP запрещён в контейнере | см. ниже |

### ICMP в Docker

- Debian-овский `ping` имеет file-capability `cap_net_raw=ep`, поэтому непривилегированный
  пользователь пингует **без** `cap_add` (проверено живым запуском от `nobody`).
- Если capability недоступны (`no-new-privileges`, `cap_drop: NET_RAW`, экзотическая ФС),
  работает второй путь — `sysctls: net.ipv4.ping_group_range` из compose.
- Ошибка прав даёт **код возврата 2**, а не 1. Бот это различает: код 2 → сообщение
  «проблема окружения», а не «адрес недоступен».
- При старте выполняется `preflight`: если ICMP не работает, бот **не запускается** и пишет
  инструкцию. Это специально: иначе он молча считал бы все адреса мёртвыми и слал ложные алерты.
- Сканирование чужих сетей из bridge-сети идёт через NAT хоста и обычно работает;
  если нужен «вид как с самой машины» — `network_mode: host` (Linux).

## Супергруппа с темами (topics)

Алерты уходят не «в чат вообще», а в конкретную тему: `chat_id` + `message_thread_id`.

**Как узнать оба числа за 10 секунд:**

1. Добавь бота в супергруппу (право «Отправка сообщений»; в темах — «Отправка сообщений в темах»).
2. Напиши `/id` **прямо в нужной теме**. Бот ответит в этой же теме:
   ```
   chat_id: -1001234567890
   твой user_id: 123456789
   id темы: 4242
   ```
3. Впиши в `.env`: `ALERT_CHAT_ID=-1001234567890`, `ALERT_THREAD_ID=4242`, перезапусти бота.

Команда `/id` работает даже при включённом privacy mode — команды боты видят всегда.
Альтернативный способ: ссылка на сообщение в теме `t.me/c/<внутренний_id>/<тема>/<сообщение>` —
среднее число и есть `message_thread_id`, а `ALERT_CHAT_ID` = `-100` + внутренний id.

Что важно в реализации:

- `message_thread_id` нужен **только при отправке** (`send_message`, `send_document`).
  Для `edit_message_text` он не нужен: сообщение адресуется по `message_id`.
- Если тема закрыта/удалена или id неверный, Telegram вернёт ошибку — тогда алерт
  **один раз** уходит в General и в лог пишется предупреждение. Алерт не теряется молча.
- `ALERT_THREAD_ID=0` — слать без темы (обычная группа или General).
- Команды, написанные в теме, бот отвечает **в ту же тему** (`/scan`, `/tree`, `/watch`, `/id`, админка).
  В личном чате никакой `message_thread_id` не передаётся.

## Решения, которые держат логику простой

- **Лимит пингов** — новый `asyncio.Semaphore` на каждый скан, поэтому `resize()` не нужен: изменение применяется со следующего скана.
- **Один скан на пользователя** — `BUSY: set` + `try/finally`, без TTL: флаг снимается и при ошибке, и при отмене.
- **Отмена** — `asyncio.Event`, а не `task.cancel()`: не нужно разбирать `CancelledError`.
- **Удаление IP** — `mon:rm:<индекс>` в списке нажавшего, а не упаковка адресов в 64 байта.
- **Цикл мониторинга** — один `while True` с `try/except` внутри: это и есть supervisor.
- **Сначала пингуем объединение всех IP один раз, потом решаем, что слать** — без вложенных циклов «юзер → его IP».
- **Результат ping** — по коду возврата (на Windows плюс `ttl=`), вывод не парсится.
- **Запись JSON** — `tmp` + `os.replace`, синхронно, без `await` внутри, поэтому корутины не могут перемешаться и `asyncio.Lock` не нужен. Если перейдёшь на асинхронные файлы — верни lock.
- **Статусы меняет только фоновый тик.** Ручная кнопка «Проверить сейчас» статусы не пишет, иначе она «съест» будущее изменение и алерт не придёт.
- **Middleware** берёт пользователя из `data["event_from_user"]`: у `Update` в aiogram 3 **нет** поля `from_user`.
- **Темы супергруппы** — один помощник `sender.thread_kwargs(message)`: есть тема → передаём `message_thread_id`, нет → пустой словарь. Никаких отдельных «режимов группы».
- **Прогресс скана** отсчитывается от `time.monotonic()` на старте, а не от нуля: иначе первый же пинг делал лишний edit.
- **Проверка окружения при старте** (`preflight`): сломанный ICMP — фатально (иначе бот врёт «всё мертво»),
  недоступный Telegram — пробуем прокси участников, а polling перезапускается с восстановлением.
- **SQLite вместо JSON**: одна точка правды, транзакции, WAL+FULL. Публичный API хранилища не изменился,
  поэтому хендлеры не переписывались.
- **Статусы прокси** — маленький автомат: `waiting → up → down → up`, `waiting → expired`.
  Никаких отдельных «менеджеров» и очередей: один цикл, один проход, одни и те же правила.

## Windows-нюансы

- Флаги ping выбираются автоматически: `-n 1 -w 1000` против `-c 1 -W 1`.
- Windows может вернуть код 0 при «Destination host unreachable», поэтому там дополнительно требуется `ttl=` в выводе.
- `asyncio.create_subprocess_exec` работает на стандартном Proactor-цикле (Python 3.8+ по умолчанию) — ничего менять не нужно.
